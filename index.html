Delivery Application Assessment

The system I am assessing is a delivery application. It is used by customers to order food, by restaurants to receive and prepare orders, and by drivers to deliver them. The system follows an availability-focused design because it must provide its services at all times. Since it operates online, users expect it to function 24/7 without interruptions.

The delivery application has a dynamic usage pattern. Traffic typically spikes between 12:00 PM and 3:00 PM during lunchtime, and again between 7:00 PM and 10:00 PM during dinner time. During these peak hours, the system must handle a large number of simultaneous users, orders, and payment transactions. Therefore, scalability and performance are very important to maintain smooth operation.

The most critical dependability attribute for this system is availability. If the system goes down, customers cannot place orders, restaurants cannot receive requests, and drivers cannot access delivery details. This would result in financial losses, damaged reputation, and customer dissatisfaction. Reliability is also important, as orders must not be lost or duplicated, and payments must be processed correctly.

In addition, the system must ensure security by protecting user data such as addresses, phone numbers, and payment information. Any data breach could significantly harm user trust. Maintainability is also crucial to allow updates and feature additions without disrupting service. Overall, the delivery application must be highly dependable to maintain continuous service, especially during peak demand periods.

Proposed Strategy – Microservices Architecture

To further improve dependability, the system can adopt a microservices architecture, where each major component—customer ordering, restaurant management, and driver delivery—is implemented as an independent service. This separation allows each service to scale, update, and fail independently, improving availability, maintainability, and performance while ensuring continuous operation even under peak load.

WEEK 07–08

CLASS 03 · Safety Engineering

Topics: Hazard → Accident → Damage, ALARP Triangle, Fault Tree Analysis, Safety Case

My Evidence (V2):

  1. Hazard → Accident → Damage (The Chain)
    • Hazard: A database sync error occurs between the app and the restaurant, causing an "Allergy: Peanuts" tag to be dropped from an order.
    • Accident: The kitchen prepares the meal with peanut oil, and the customer consumes it.
    • Damage: The customer suffers a severe allergic reaction (Anaphylaxis), leading to potential hospitalization or death.
    • Intervention: You break this chain by implementing a Protection System that cross-checks the order JSON against the user's saved health profile before the "Submit" button is even enabled.


  2. The ALARP Triangle

    Since absolute safety is often impossible, you must balance risk against the cost and difficulty of reducing it.

    • Intolerable Risk: An unauthorized user gaining access to the delivery rider’s real-time home address. This must be designed out of the system entirely.
    • ALARP (As Low As Reasonably Practicable): The risk of a rider’s phone battery dying mid-delivery. You tolerate this risk because it is impractical to prevent entirely, but you reduce it by having the app send a low-battery alert to the server to reassign the order if necessary.
    • Acceptable Risk: A customer receiving a slightly cold meal due to traffic. The risk is negligible to physical safety and is tolerated by society.

    The ALARP Triangle digram



  3. Fault Tree Analysis (Deductive)

    Fault Tree Analysis is a top-down deductive technique used to identify the root causes of a system failure.

    • Top Event: This is the primary hazard you are trying to prevent, such as "User receives incorrect medication/special dietary meal".
    • OR Gate (Single Point of Failure): An OR gate represents a single point of failure where any one cause can trigger the hazard. In your app, the hazard occurs if the restaurant’s tablet fails OR the driver picks up the wrong bag.
    • AND Gate (Redundancy): An AND gate is used to design redundancy into the system. To prevent an "Incorrect Calculation" of fees, both the primary algorithm AND the secondary verification monitor must fail simultaneously for the error to reach the user.

🛡 Resilience Case

Assignment 6 — Evolving TANDIB from reliable to resilient by designing for real failure modes found in the actual codebase.

1. Failure Chain Analysis

The fault was found in a real file: AutoAcceptOrderJob.php. TANDIB fires this job 10 seconds after a customer places an order (when the restaurant has auto-accept enabled). The job checks the order status without a database lock, while OrderController::cancel() writes to the same record without guarding against the concurrent job.

Fault (Static Defect)

In AutoAcceptOrderJob::handle(), the guard:
if ($order->status !== STATUS_PENDING) return;
runs without a transaction lock. The wallet top-up in OrderController::store() correctly uses lockForUpdate(), but the order status transition does not — an inconsistency in the same codebase.

Error (Incorrect Internal State)

Both the cancel request and the job read status = pending at the same millisecond. The cancel writes cancelled; the job then overwrites it with confirmed (or vice versa). The order record now holds a status that contradicts the customer's action.

Failure (Visible Deviation)

The customer sees "Order Cancelled" in the app. The restaurant receives an Expo push notification saying "New Order Confirmed" and begins preparation. A real meal is made and a driver is assigned for an order the customer already cancelled — causing financial loss and driver-wasted trips.

2. Recognition & Resistance (R&R) Strategies

Type Strategy Name How It Works in TANDIB (specific to actual code) Threat Addressed
Recognition Laravel Telescope Anomaly Alert TANDIB already has Laravel Telescope installed (migration: create_telescope_entries_table). A custom Telescope watcher monitors for impossible order status transitions (e.g., cancelled → confirmed). When detected, it logs a tagged entry and triggers a Filament admin dashboard notification before the restaurant receives the push. Detects the race condition error in the DB before the Expo push notification is dispatched to the restaurant
Recognition Expo Push Delivery Receipt Audit TANDIB's ExpoPushService sends notifications fire-and-forget. Adding receipt polling (Expo's /push/getReceipts endpoint) detects when a "confirmed" push was delivered to the restaurant after the order was already cancelled — surfacing the inconsistency to the ops team. Catches the failure even when it slips past the DB layer, before the restaurant acts on the incorrect notification
Resistance DB Transaction Lock in AutoAcceptOrderJob Wrap the status check in AutoAcceptOrderJob::handle() inside a DB::transaction() with lockForUpdate() — matching the pattern already used in OrderController::store() for the wallet balance. This guarantees that cancel and auto-accept cannot both see pending at once. Eliminates the race condition at the source — the fault can no longer produce an error state
Resistance Laravel Queue with FIFO Ordering TANDIB already uses Laravel's queue system (AutoAcceptOrderJob implements ShouldQueue, and the create_jobs_table migration exists). Configuring the queue driver to process order-state jobs in strict FIFO order ensures that a cancel job dispatched before the 10-second auto-accept fires will always be processed first, even under worker load. Maintains critical service delivery (no ghost orders) even during queue worker backpressure at peak hours

Technical Layer

  • lockForUpdate() in AutoAcceptOrderJob: prevents concurrent status reads
  • DB::transaction() wrapper: already used for wallet — extend to order status
  • FIFO Laravel Queue: ensures cancel jobs are processed before auto-accept jobs
  • Laravel Telescope: already installed — add status-transition anomaly watcher

Hole: A DB deadlock under extreme load could cause both the cancel and the lock to time out — both fail silently.

Human Layer

  • Filament Admin Dashboard: already built — add ghost-order alert widget
  • Expo Push Receipt Audit: a team member reviews delivery receipts for mismatch patterns daily
  • Complaint System: the Complaint model and ComplaintController already exist — customer reports feed directly into the ops team

Hole: Human review is reactive — the restaurant may already have started cooking before a human sees the flag.

Organizational Layer

  • Railway Deployment Policy: the Procfile and railway.json enforce controlled deployments — no hot-patching of queue workers during peak hours (12–2 PM, 7–10 PM)
  • Blameless Post-Mortem: every ghost-order incident triggers a root-cause review before the next feature is shipped
  • Restaurant SLA Agreement: restaurants are briefed that a "confirmed" push must be cross-checked against the in-app order panel before kitchen preparation begins

Hole: Restaurant staff may not follow the SLA brief under high order volume — human compliance degrades under pressure.

4. The Sociotechnical Factor — Human-in-the-Loop

When Automated Resilience Reaches Its Limit

The DB lock and FIFO queue handle the race condition automatically. But if the queue worker itself crashes mid-job (e.g., Railway restarts the container during peak load), the auto-accept job may be lost entirely — leaving the order stuck in pending with no driver assigned and no customer notification.

At this point, the Filament admin panel (already built into TANDIB) is the human interface:

  • The admin sees orders stuck in pending beyond the expected 30-second window via a stale-order widget.
  • They manually trigger the order status update via the Filament resource panel (MenuController::updateOrderStatus() is already accessible).
  • They use the Complaint System (AdminComplaintController::reply()) to contact the affected customer with a compensation credit to their wallet.
  • They escalate to Railway support if the container restart pattern indicates an infrastructure fault rather than a code fault.

The human expert is not a fallback of last resort — they are a designed layer in the Swiss Cheese model, operating on tools that were built into TANDIB from the start.

♻ Reuse Strategy

Assignment 7 — How TANDIB was built by strategically reusing proven components, and how those reuse decisions directly reinforce the resilience goals from Assignment 6.

1. Position in the Reuse Landscape

Chosen Approach: Application Frameworks + COTS Service Integration

TANDIB is built on the Application Frameworks reuse strategy. The entire backend is a Laravel application — a full-stack PHP framework that provides routing, ORM (Eloquent), authentication scaffolding, job queues, and testing infrastructure out of the box. On top of it, three COTS (Commercial Off-The-Shelf) services are integrated: Stripe for payments, Expo for push notifications, and Railway for deployment.

Justification via Planning Factors:

Planning FactorTANDIB's ContextWhy Application Framework Reuse Fits
Development Schedule Semester project — the entire system (backend + mobile) built by a small team in one semester Laravel's built-in auth, migrations, and job queue meant the team never wrote a login system, queue broker, or DB schema manager from scratch. Expo + React Native gave them a cross-platform mobile app without native iOS/Android expertise.
Team Skills Team has PHP/web background; mobile is secondary Laravel is the most documented PHP framework. Expo abstracts native mobile APIs behind JavaScript — the team could build DeliveryController (driver GPS tracking) without writing a single line of Swift or Kotlin.
Software Criticality Payment processing is financially critical; push notifications are operationally critical (restaurant must know instantly about new orders) Reusing Stripe (PCI-DSS certified) and Expo (battle-tested at scale) is demonstrably safer than writing custom payment or notification systems. The team cannot replicate the validation those services have accumulated.

2. Product Line Architecture (SPL)

Core Components (Generic — Reused Unchanged)

These are proven building blocks used as-is. TANDIB's team did not modify their internals.

  • Laravel Framework — Provides routing (api.php), Eloquent ORM (all 20+ Models), Sanctum auth (auth:sanctum middleware), queue system (ShouldQueue in AutoAcceptOrderJob), and migrations.
  • Laravel Sanctum — Bearer-token authentication. Every protected route in api.php uses middleware('auth:sanctum') with zero custom auth code.
  • Stripe PHP SDK — \Stripe\Checkout\Session handles card payment initiation and verification in PaymentController. PCI-DSS compliance is inherited, not built.
  • Expo Push Notifications — ExpoPushService wraps Expo's HTTP API. The ExpoPushToken model stores device tokens; the service sends typed notifications (new order, status update) to customers and restaurant managers.
  • Laravel Telescope — Installed for monitoring (migration: create_telescope_entries_table). Logs every API request, queue job, and database query in development and staging.
  • Filament Admin Panel — Full admin interface built from the app/Filament/ directory. Used for managing restaurant applications, complaints, and order oversight without writing custom HTML.
  • Railway — Cloud deployment platform (configured via Procfile and railway.json). Handles container builds, environment variables, and automatic restarts.

Specialized Components (Built on Core — Configured for TANDIB)

These are TANDIB-specific. They extend the core framework to serve the food-delivery domain.

  • Order State Machine — 10 statuses (pending → confirmed → accepted → preparing → ready → picked_up → on_the_way → arrived → delivered / cancelled / rejected) defined in Order.php as constants. The transition logic is spread across OrderController, MenuController, and AutoAcceptOrderJob.
  • AutoAcceptOrderJob — A custom queue job that auto-advances a pending order to confirmed 10 seconds after placement if the restaurant has opted in. This is the job where the Fault from Assignment 6 was identified.
  • Haversine Delivery Zone Calculator — Custom geographic fee engine in OrderController::haversineMeters() and PaymentController::haversineMeters(). Calculates distance between restaurant GPS and customer GPS to determine which DeliveryZone fee applies.
  • Wallet System — WalletTransaction model, wallet balance on User, and wallet deduction logic inside the checkout transaction. Uses lockForUpdate() to prevent double-spend — the resilience pattern that should be extended to order status (Assignment 6 fix).
  • Promo Code Engine — PromoCode model with isValid() and calculateDiscount() business logic, validated and applied during checkout in OrderController::store().
  • Complaint & Admin Reply System — ComplaintController for customers to file complaints; AdminComplaintController for the ops team to respond. Part of the Human Layer in the Swiss Cheese model.

3. Validation & "The Ariane 5 Lesson"

Thorough Validation Plan for Reused Components

  • Stripe Test Mode: All payment flows in TANDIB are tested against Stripe's sandbox environment (not mocked). This matches the Ariane 5 lesson — the reused component must be validated in the actual operational context, not a simulated one.
  • Laravel PHPUnit Integration Tests: The phpunit.xml is already configured. Tests exercise the full HTTP stack (real DB, real queue worker) — not unit tests that mock Eloquent. If a migration changes a column, the test breaks immediately.
  • Boundary Value Tests for Payment Amounts: Checkout is tested at SAR 0.01 (minimum), SAR 0.00 (wallet-covered), and amounts that produce floating-point edge cases (e.g., SAR 29.99 × 100 = 2998.9999...).
  • Expo Push Receipt Polling: After sending notifications, a scheduled job checks Expo's receipt endpoint to confirm delivery — validating that the reused push service behaved as expected in production.

Reliable Programming Commandment (Ariane 5 Applied to TANDIB)

The Ariane 5 rocket failed because a 64-bit float was reused from Ariane 4 in a context that produced a value too large for the 16-bit integer it was converted into — a silent overflow, never tested in the new operational envelope.

The same risk exists in TANDIB today. In Order.php:

'subtotal' => 'float', 'total_price' => 'float'
All monetary fields are cast to PHP float (IEEE 754 double-precision). The conversion (int) round($remainingTotal * 100) in PaymentController is a bandage — it masks the precision loss rather than eliminating it.

Commandment enforced going forward:

"All monetary values in TANDIB MUST be stored as integers (halalas: 1 SAR = 100 halalas) in the database and in all PHP calculations. Convert to SAR decimal only at the API response layer. PHP's float type is forbidden in any class that touches order totals or payment amounts."

4. Industry Alignment

Industry Trend: Cloud-Native Deployment (Railway + Laravel Horizon)

TANDIB's reuse strategy directly leverages the Cloud Computing trend. Railway (configured via railway.json and Procfile) provides:

How Cloud-Native Supports Isolation (Resilience Link):

  • Automatic Container Restarts: If the PHP-FPM process serving the API crashes, Railway restarts it within seconds — directly supporting the Availability attribute from Week 03–04.
  • Environment Variable Isolation: Stripe keys, DB credentials, and Expo tokens are injected at runtime — never in source code. A compromised key can be rotated without a redeployment.
  • Queue Worker as Separate Process: The Procfile can run the queue worker (php artisan queue:work) as an independent worker process — meaning a job failure (AutoAcceptOrderJob) cannot crash the API server handling customer requests.

How Cloud-Native Supports Recovery (Resilience Link):

  • Zero-Downtime Deployments: Railway's rolling restart means a code fix for the AutoAcceptOrderJob lock issue (Assignment 6) can be deployed without taking the API offline.
  • Laravel Horizon (next step): Adding Horizon (Redis-backed queue dashboard) to the Railway deployment would give real-time visibility into queue worker health — a direct upgrade to the Technical Layer of the Swiss Cheese model.
  • Database Backups via Railway: Automated MySQL backups ensure that even if a corrupt order write reaches the DB (Assignment 6 failure scenario), a point-in-time restore is available.

Portfolio Bridge — How Reuse Supports Resilience in TANDIB

The two assignments are not separate — they are two views of the same engineering decision:

  • The lockForUpdate() fix (Resistance strategy, Asgn. 6) is possible because TANDIB reused Laravel's DB facade and transaction API (Asgn. 7). The pattern is already proven in the wallet deduction code — reuse made the fix a one-line extension, not a redesign.
  • The FIFO queue fix (Resistance, Asgn. 6) relies on Laravel's ShouldQueue interface — a core reused component (Asgn. 7). Without the queue framework, AutoAcceptOrderJob would not exist, and the race condition would manifest as a synchronous deadlock instead.
  • The Ariane 5 Commandment (Asgn. 7) directly prevents an escalation of the Fault chain (Asgn. 6): a floating-point mismatch between calculateTotal() (PaymentController) and the Stripe verification amount (OrderController) could cause a valid payment to be rejected, triggering a ghost order through a different path.
  • The Railway cloud deployment (Asgn. 7) is what makes the Organizational Layer of the Swiss Cheese model (Asgn. 6) enforceable — change-freeze policies have teeth only when deployments are controlled through a single platform with a deployment history.

🧩 CBSE Strategy

Ch.16 — TANDIB built entirely through Development with Reuse: ten off-the-shelf components composed into a working food-delivery platform, with explicit Requires/Provides interface contracts and a measured integration risk strategy.

1. Positioning TANDIB in CBSE

Selected Approach: Development with Reuse

TANDIB is built almost entirely by composing off-the-shelf components rather than building functionality from scratch. This is Development with Reuse — the system architect's job is to identify, select, adapt, and integrate existing components rather than design new ones. The alternative, Development for Reuse (building generalized components intended for others to reuse later), is inappropriate for a startup-stage MVP where the priority is a working product, not a component library.

Justification via Planning Factors:

Planning FactorHow It Favored Development with Reuse
Budget A single-developer MVP cannot afford to implement an authentication system, admin dashboard, push notification pipeline, or map SDK from scratch. Each of these exists as a production-grade off-the-shelf component.
Development Schedule TANDIB had to reach a demonstrable state within an academic semester. Composing Expo + Laravel + Supabase compressed what would be 6+ months of infrastructure work into integration configuration.
Market Availability Every critical capability TANDIB needs has a mature, well-documented open-source or managed component available — auth (Sanctum), admin UI (Filament), database (Supabase), maps (React Native Maps), notifications (Expo Notifications). The market is saturated with high-quality reusable components for this problem domain.

Key Interface Contracts

  • Mobile → Backend: Every API call in mobile/services/api.ts sends an Authorization: Bearer <token> header. Laravel Sanctum's middleware validates this token before the request reaches any controller. This is a strict Requires/Provides contract: the mobile component requires a valid token, Sanctum provides the validation.
  • Filament → Eloquent: Filament 5 requires Eloquent model classes with defined $fillable fields and Policy classes for access control. The models provide query builders and relationship resolution that Filament renders as table rows and form fields.
  • Backend → Supabase: Laravel's Eloquent ORM requires a DATABASE_URL environment variable pointing to Supabase's connection pooler. Supabase provides a standard PostgreSQL wire-protocol interface — no Supabase SDK is needed; it behaves as a plain PostgreSQL instance.

3. Validation & Risk Measurement

Integration Testing Plan

Component-level unit tests are insufficient for CBSE — what matters is that the interfaces between components behave correctly under real conditions. TANDIB's integration testing plan targets each interface boundary:

Interface BoundaryTest Approach
Mobile ↔ Laravel API Postman/HTTP test collection runs against the live local backend. Every endpoint is tested with valid tokens, expired tokens, and missing tokens to verify Sanctum's middleware rejects at the correct boundary.
Sanctum ↔ Users Table Laravel Feature tests (PHPUnit) create a real database user, issue a token, and assert authenticated routes return 200 while unauthenticated routes return 401 — no mocking.
Filament ↔ Policy Classes Automated browser tests (or manual walkthroughs) confirm that a restaurant_owner session cannot navigate to admin-only Filament resources, even via a direct URL.
Eloquent ↔ Supabase Migration rollup tests run php artisan migrate:fresh against a staging Supabase project to confirm all 27 tables are created correctly with all constraints intact.
Expo Notifications ↔ Device End-to-end test: trigger an order status change via the API and confirm the push notification appears on a physical device within an acceptable latency window.

Identified Risk: Silent Version Mismatch

React Native Maps, Expo Router, and Expo Notifications are each maintained by separate teams on independent release cycles. A patch update to one package can silently break its interface with another — for example, an Expo SDK 54→55 upgrade may change the push token format that Expo Notifications provides, while the backend's NotificationController was written expecting the SDK 54 format. The app continues to compile and launch, but push notifications silently stop delivering.

This is the most dangerous class of CBSE failure: no crash, no error log, just silent loss of functionality.

Mitigation Plan

  • Exact version pinning in package.json — no caret (^) or tilde (~) ranges for Expo ecosystem packages. Upgrades are explicit, deliberate decisions.
  • Expo's official compatibility matrix is consulted before any SDK upgrade to confirm which versions of each native package are compatible.
  • Staged upgrade policy: any dependency upgrade is first applied to a feature branch and the full integration test suite — including a live push notification delivery test — must pass before merging.
  • Mandatory changelog review for any package touching the Requires/Provides interface boundary (Sanctum, Expo Notifications, Supabase client library).

4. Industry Alignment

Trend: Composable Architecture (API-First Design)

TANDIB's CBSE strategy aligns directly with the Composable Architecture trend that has become the standard for modern platform engineering. The principle is that every capability is exposed through a well-defined API interface — making components independently deployable, replaceable, and testable.

In TANDIB this is realized concretely: the mobile app, the Filament admin panel, and any future web frontend all consume the same Laravel REST API. No component has privileged direct access to the database — all interaction goes through the API interface layer. This means:

  • Efficiency: A new client (e.g., a restaurant tablet app) can be added by building a new consumer of the existing API — no backend changes required.
  • Replaceability: If Supabase were replaced with a self-hosted PostgreSQL instance, only the DSN connection string changes. Eloquent's interface to the rest of the system remains identical.
  • Isolation: When the mobile app is updated, the backend components are unaffected because the API contract is the stable boundary between them.
  • This composable, API-first design is what makes CBSE practically achievable at TANDIB's scale — each component can evolve independently as long as it honors its interface contract.

How CBSE Supports Efficiency Goals

Every off-the-shelf component integrated into TANDIB represents a category of engineering work that was not performed from scratch — authentication logic, admin UI generation, encrypted storage, push notification delivery, and geographic map rendering. The team's actual effort was spent on the business logic unique to food delivery: order workflows, promo code validation, geo-fenced restaurant discovery, and role-scoped data access.

CBSE made that focus possible by making the infrastructure a composition problem rather than an implementation problem.

🌐 Distributed Architecture

Ch.17 — TANDIB's runtime is distributed across five independent nodes. The architecture ensures no single failure brings down the platform, every inter-node channel is encrypted with TLS 1.3, and three managed cloud services absorb infrastructure complexity so the team can focus on business logic.

1. Positioning TANDIB in the Distributed Landscape

Selected Model: Multi-Tier Client-Server Architecture

TANDIB is a classic three-tier client-server system, distributed across geographically separated nodes: mobile client devices, a cloud-hosted application server, and a managed database service. This is the correct model because TANDIB's core requirement is resource sharing with centralized authority — all users (customers, restaurant owners, admins) must read and write a shared, consistent dataset.

Peer-to-peer is ruled out because the data must be authoritative and consistent across all clients. A pure distributed component architecture (microservices) is ruled out because the team size and scale do not justify that operational complexity at this stage.

Justification Based on System Requirements:

RequirementWhy Client-Server Fits
Shared data consistency All users read from and write to the same PostgreSQL database. The centralized server enforces business rules (promo validation, geo-fencing, order state machine) before any write reaches the database.
Peak load handling The application server tier is the only layer that needs to scale horizontally. The database (Supabase) and mobile clients are independently managed — scaling the API layer does not require touching either.
Multiple client types The same Laravel API serves mobile customers, mobile restaurant owners, and the Filament web admin panel. A single server interface handles all client types without client-side coordination.
Security boundary Centralizing business logic in the server tier means no client device ever has direct database access. All data passes through Laravel's authentication and authorization middleware.

3. Reliability & Security

Failover Plan

TANDIB's distributed design isolates failures so no single node failure crashes the entire platform. Each scenario below maps a node failure to its exact blast radius and recovery path:

Scenario 1 — Application Server Down

  • Mobile app receives a network timeout or 5xx response — displays a user-friendly offline error screen instead of crashing.
  • Filament admin panel becomes inaccessible, but it is an internal tool and does not affect active customer sessions.
  • Recovery: The cloud host detects the unhealthy instance and restarts it automatically — typically within 60–90 seconds. Supabase data is completely unaffected.

Scenario 2 — Supabase (Database) Outage

  • Laravel returns 500 errors for any request requiring a database read or write.
  • Mobile app receives structured error responses and shows a service-unavailable message.
  • Recovery: Supabase provides automatic point-in-time recovery — once restored, the database state is consistent to within seconds of the outage. Nodes 4 and 5 continue independently.

Scenario 3 — Mobile Device Loses Connectivity

  • Zustand cart state persists in memory for the session duration — items in the cart are not lost during a momentary network drop.
  • API calls are retried with exponential backoff before surfacing an error to the user.
  • The app degrades gracefully to a read-only offline state until connectivity is restored — no crash.

Scenario 4 — EAS / OTA Update Fails

  • The app continues running the previously installed bundle.
  • EAS updates are additive and non-blocking — if an update cannot be fetched, the existing working version runs.
  • No user-visible disruption. The next successful check delivers the pending update silently.

Security Protocol: TLS 1.3 Across All Inter-Node Communication

Every data transfer path in TANDIB is encrypted in transit using TLS 1.3:

  • Mobile → Laravel: HTTPS enforced at the cloud host level. HTTP requests are redirected to HTTPS. The mobile app's API base URL is https:// — no plaintext fallback.
  • Laravel → Supabase: Supabase requires SSL connections by default. The DATABASE_URL environment variable includes ?sslmode=require, making the TLS requirement explicit and enforced at connection time — a plaintext connection attempt is rejected by the database server.
  • Authentication tokens (Sanctum bearer tokens) are transmitted only over these encrypted channels and stored only in Expo SecureStore on the device — never in AsyncStorage, never in cookies, never logged.

TLS 1.3 specifically eliminates the handshake round-trips present in TLS 1.2, reducing connection establishment latency — a performance benefit on top of the security requirement.

4. Industry Alignment: Cloud Computing & SaaS

TANDIB's distributed architecture directly leverages Cloud Computing and SaaS at three of its five nodes, dramatically reducing infrastructure cost and operational burden:

Supabase — BaaS/SaaS (Node 3)

Supabase is a fully managed database-as-a-service. TANDIB gets connection pooling, automated daily backups, point-in-time recovery, and geographic redundancy — all without operating a single database server. The cost scales with actual usage rather than requiring a reserved server. For a startup-stage product this is the difference between viable and not.

EAS — Expo Application Services (Node 5)

EAS replaces what would otherwise require a dedicated CI/CD server with Apple and Google developer toolchains installed. It provides on-demand build capacity: when a new version is ready, EAS compiles the iOS .ipa and Android .apk, runs code signing, and submits to both app stores from a single CLI command. The OTA update system means critical bug fixes reach all live devices within minutes of deployment, without waiting for an app store review cycle.

Cloud-Hosted Laravel — IaaS (Node 2)

The Laravel application server runs on a managed cloud platform (Railway or DigitalOcean App Platform). This provides automatic restarts on failure, environment variable management, one-command deployment from a Git push, and horizontal scaling by adding instances behind a load balancer — none of which require managing physical servers or configuring Linux from scratch.

Combined Effect

The three managed cloud services (Supabase, EAS, cloud host) together handle infrastructure reliability, scaling, security patching, and backups. The development team's entire effort is focused on application code — the food delivery business logic — rather than infrastructure operations. This is the practical definition of how cloud computing supports efficiency and resilience simultaneously.

Distributed Design Supporting Continuity

TANDIB's distributed architecture is designed so that no single node failure brings down the entire platform. The database, the application server, the push gateway, and the build/distribution system are all independent nodes with no circular dependencies. A crash in any one of them degrades exactly one capability while the rest continue.

  • Supabase's managed replication ensures data is never lost.
  • EAS's OTA system ensures fixes reach users without a full release cycle.
  • TLS 1.3 across every inter-node channel ensures data in transit cannot be read or tampered with.

This is continuity by design, not by luck.

The testing pyramid describes the optimal distribution of test types: many fast, cheap unit tests at the base; fewer integration tests in the middle; and a small number of end-to-end tests at the top. 5. Coverage Metrics

Code coverage measures what percentage of the application's source lines, branches, and paths are executed during the test suite. PHPUnit generates an HTML report using Xdebug or PCOV. 

cd backend
XDEBUG_MODE=coverage php artisan test --coverage --min=70

The --min=70 flag fails the test run if overall coverage drops below 70% — enforced as a CI gate before any merge.

LayerTargetRationale
Business logic (Models, calculation methods) 90%+ Haversine, isCancellable(), promo math — pure logic, easy to test, high impact if wrong
API Controllers (Controllers/Api/) 80%+ Every endpoint covered by at least one happy-path and one negative-path feature test
Middleware & Form Requests 70%+ Auth middleware and validation rules are tested indirectly through feature tests
Filament Resources Not targeted Admin UI resources are configuration-driven; testing Filament internals is not productive
Mobile (Zustand store) 80%+ Cart logic is pure and high-value; UI screens are lower priority

What Coverage Does NOT Measure

Coverage reports that a line was executed — not that the assertion was correct. A test that calls placeOrder() and asserts only assertStatus(200) gives full line coverage but does not verify the order total, the payment record, or the notification dispatch. Coverage is a floor, not a ceiling. TANDIB's tests assert specific JSON paths, specific status codes, and specific database states — not just that the endpoint responded.

⚖️ Safety vs Reliability — My understanding

"A system can perfectly follow its specification and still cause harm. Safety is freedom from harm, Reliability is conformance to spec. A reliable weapon is still dangerous — that insight changed everything."

💼 What I will carry into my career

"The burden of proof is on the engineer. In safety engineering, you are guilty until proven innocent. I will never ship a critical system without a Safety Case — and I now know how to build one."
